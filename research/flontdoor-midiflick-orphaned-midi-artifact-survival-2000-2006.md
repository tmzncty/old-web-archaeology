# FlontDoor / MIDIFlick：社区消失后 MIDI 本体幸存、作品语境断裂（2000s）

> Status: **comparative research checkpoint / artifact probe**, not a complete M1 case.
>
> Scope note: 本仓主线仍是约 1995—2015 年中文旧网。FlontDoor 是日本 MIDI 社区，因此这里只作为一个**比较性样本**进入：它能直接帮助解释旧 Web 中“文件仍在，但作者、标题、索引、评论与社区关系一起丢失”的保存断裂。它不把本仓改造成日本互联网史项目。
>
> 本轮目标也不是重新分发历史 MIDI。版权 / 许可不明时，本仓只保存 locator、metadata、证据分级与分析。

## 0. 为什么这个样本值得记录

旧 Web 保存研究很容易默认：

```text
page survives
or
page disappears
```

FlontDoor 暴露的是更细的状态：

```text
community
!= site index
!= user profile
!= work metadata
!= comments / social context
!= binary MIDI object
!= archive locator
!= playable reconstruction
```

其中最值得研究的极端情况是：

> **二进制作品对象可能幸存，而它在社区中的身份几乎完全消失。**

当前样本是一个候选 MIDI：

```text
filename: kanashii.mid
historical path: /flontdoor/user/rop/kanashii.mid
candidate Wayback locator:
https://web.archive.org/web/20021031010422if_/http://www.rukaf.net/flontdoor/user/rop/kanashii.mid
```

这个 locator 的 timestamp string 是 `20021031010422`。

但本轮研究环境无法实际打开 / 下载该 Wayback 对象，因此严格按 `docs/METHOD.md` 处理为：

```text
candidate locator only
!= verified historical capture
!= verified byte payload
```

不能仅凭 URL 中的 timestamp 写成“该文件已经被本轮直接验证为 2002-10-31 的 archive artifact”。

## 1. FlontDoor 与 MIDIFlick 的关系：至少到 2005 年仍可由同期材料确认

2005-11-06 的 2ch / DTM 讨论保存副本中，有用户直接推荐：

```text
MIDIFlick
http://www.rukaf.net/flontdoor/
```

来源：

- 「最も簡単なDTMソフトは何？」的论坛转录，包含 2005-11-06 发言：
  <https://music2chan.blog88.fc2.com/blog-entry-64.html>

Evidence:

- grade: **B**（同期论坛内容的后来转录；不是 FlontDoor 自身页面）
- supports:
  - 2005 年晚期 `www.rukaf.net/flontdoor/` 被用户直接识别为 MIDIFlick 的站点入口；
  - MIDIFlick 当时仍处在实际用户讨论与推荐中。

这不足以证明：

- FlontDoor 的精确成立日；
- 当时站内作品总数；
- 站点全部功能；
- 2005 页面 DOM / charset / 下载结构。

## 2. 2006 年中站点消失：目前最强证据是用户 / 避难所建立者的同期记录

2006-06-30，葉月まっつん在个人博客中写到：

- 自己音乐活动的起点是面向初学者的 MIDI sequencer `MIDIFlick`；
- 其“总本山” FlontDoor 已经“消滅”；
- 因为不希望用户就此散掉，自己建立了“避難所”；
- 当时仍无法联系原管理者，也不知道能否在避难所代理分发 MIDIFlick。

来源：

- 葉月まっつん, 「FlontDoor」, 2006-06-30:
  <https://blog.livedoor.jp/dtm_0714/archives/50517192.html>

Evidence:

- grade: **B / participant-near-primary**
- page date: 2006-06-30
- supports:
  - 到 2006-06-30，核心用户已经把原站状态描述为“消滅”；
  - 避难所建立是对原社区失联 / 消失的直接应对；
  - 原管理员在当时至少处于无法联系的状态。

这里仍不应把“消滅”自动等价为：

- 有正式关站公告；
- 服务器数据已经永久删除；
- 2006-06-30 就是法律 / 运营意义上的正式终止日。

更稳妥的写法是：

> **2006 年中，FlontDoor 原站发生长期不可用 / 消失，社区成员随后建立避难所。**

- 避难所：`http://music.geocities.jp/xhqjs083/flont_door/`

- 2006-07-28：“中の人が変わりました”。

来源：

- <https://mixi.jp/view_community.pl?id=542228>

Evidence:

- grade: **B/C boundary**
- 原因：当前 live Mixi page 保留旧文本，但不是 2006 年 archive capture；页面内容本身包含明确的 2006 dated notes。
- supports:
  - 原站与避难所 URL 的关联；
  - 社区成员对故障 / 长期离线的同期式记录；
  - 避难所不是研究者今天推断出来的后设名称，而是当时社区实际使用的称呼。

## 4. 后来回忆证明：FlontDoor 不只是下载页，而是作品投稿与互动社区

2023 年，一位昔日用户回忆：

- 在二十代前半接触 MIDIFlick；
- 用它创作过若干曲子；
- FlontDoor 允许用户投稿作品；
- 投稿后会收到感想；
- 用户会与在站内认识的人合作作曲。

来源：

- chrysalisys, 2023-09-08:
  <https://chrysalisys.hatenablog.com/entry/2023/09/08/010957>

Evidence:

- grade: **C**（多年后的参与者回忆）
- strong for:
  - 当事人的使用经验；
  - “投稿—反馈—合作”的社区记忆。
- not sufficient for:
  - 精确页面结构；
  - 作品数量；
  - 具体投稿日期；
  - 某一 URL 在某年必然存在。

另一个仍在线的个人作品页也回忆 FlontDoor / MIDIFlick，并把 2004 年作品与当时站内企划联系起来：

- <https://sites.google.com/site/emonagikalbi/music>

Evidence:

- grade: **C**
- supports:
  - MIDIFlick / FlontDoor 与 2000 年代前半个人 MIDI 创作活动的持续联系。

这些回忆彼此独立时，可以帮助确认社区性质，但不能替代历史 capture。

## 6. 避难所的第二次平台死亡：GeoCities Japan 终止

FlontDoor 避难所使用：

```text
music.geocities.jp/xhqjs083/flont_door/
```

Yahoo! Japan 的官方通知确认 Yahoo! GeoCities 在 **2019-03-31** 结束服务，2019-04-01 之后页面将逐步不可访问。

来源：

- Yahoo! Domains official notice, 2019-01-11:
  <https://notice.yahoo.co.jp/domains/archives/2019011101.html>

JPNIC 时间线也记录日本版 GeoCities 于 2019-03-31 关闭：

- <https://www.nic.ad.jp/timeline/en/>

ArchiveTeam 对 GeoCities Japan 的记录则把保存状态标为 **Partially saved**，并记录 2018 年抢救 crawl 的规模与关闭时间：

- <https://wiki.archiveteam.org/index.php/GeoCities_Japan>

因此可以确定一条重要的保存链：

```text
FlontDoor original host
        ↓ 2006 community displacement
FlontDoor refuge on GeoCities Japan
        ↓ 2019 host shutdown
archive / mirrors / individual copies
```

这是一种 **secondary-host mortality / 二级托管再次死亡**：

> 社区为了逃离一次平台 / 主机故障而建立的“避难所”，本身仍然依赖另一个会死亡的平台。

## 7. `kanashii.mid`：目前能说什么，不能说什么

Candidate locator:

```text
https://web.archive.org/web/20021031010422if_/
http://www.rukaf.net/flontdoor/user/rop/kanashii.mid
```

### 当前可安全记录

- filename: `kanashii.mid`
- path segment: `user/rop/`
- original host candidate: `www.rukaf.net`
- site path: `/flontdoor/`
- candidate archive timestamp string: `20021031010422`

### 不能直接推出

#### 7.1 `rop` 是作者真实身份

`rop` 可能是：

- username；
- uploader namespace；
- directory identifier；
- account handle；
- 其他站内路由字段。

在没有 profile / index / author field 前，只应写：

```text
path/account identifier candidate: rop
```

不反查或扩张普通个人身份。

#### 7.2 曲名一定是《悲しい》

`kanashii` 与日语 `悲しい` 的罗马字形式相符，但 filename 可能只是：

- 临时工程名；
- 上传 slug；
- 情绪标签；
- 实际标题；
- 后台自动命名结果。

因此当前记录：

```text
display title: unknown
filename semantic hint: "kanashii" plausibly corresponds to 悲しい
status: inference only
```

#### 7.3 创作年份就是 2002

即使 candidate Wayback timestamp 最终被直接验证，它也只能先证明：

> **文件在该 capture 时间之前已经位于被抓取的 URL 上。**

它不自动等于：

- composition date；
- first upload date；
- last edit date；
- first publication date。

## 8. 本轮无法执行的 MIDI 内部元数据检查

原计划是下载该 MIDI，只检查不涉及重新分发的内部 metadata：

- sequence / track name；
- copyright meta event；
- text / marker；
- sequencer-specific event；
- MIDI format / PPQN；
- channel / program usage；
- 是否存在可识别的工程名。

但当前研究 runtime：

- Web 工具无法直接打开 Wayback binary locator；
- container 对 `web.archive.org` 的 DNS / transport 也不可用；
- 因此未取得实际字节。

Structured negative result:

```yaml
object: kanashii.mid
candidate_capture_url: https://web.archive.org/web/20021031010422if_/http://www.rukaf.net/flontdoor/user/rop/kanashii.mid
opened_capture: false
payload_obtained: false
metadata_inspected: false
failure_class:
  - archive_binary_not_opened_in_current_web_runtime
  - container_archive_transport_unavailable
unknowns:
  - file size
  - sha256
  - MIDI format
  - track count
  - sequence name
  - copyright meta event
  - embedded text
  - program/channel layout
  - whether payload is a valid Standard MIDI File
```

关键解释：

> 这不是“文件不存在”，而是“本轮没有取得可验证 payload”。

## 9. 两个当前仍未证实的数字：成立日与 56,000 首

研究线索里出现：

因此当前状态必须是：

```text
2000-05-28 founding date: UNVERIFIED LEAD
56,000+ MIDI count: UNVERIFIED LEAD
```

- 同期独立报道明确引用站点统计。

## 10. 新保存模型：`artifact survives, identity graph collapses`

这个样本最值得加入仓库的不是“又有一个站挂了”，而是下面这个状态：

```text
binary artifact survives
+
page/index metadata disappears
+
account identity becomes opaque
+
comments/reviews disappear
+
project/collaboration graph disappears
+
site-wide ordering/ranking disappears
```

暂称：

**`artifact survives, identity graph collapses / 本体幸存而身份图谱坍塌`**

这与普通 link rot 不同。

普通 link rot 关注：

```text
URL -> 404
```

这里更像：

```text
MIDI bytes -> possibly recoverable
but
"who made this?"
"what was its title?"
"when was it uploaded?"
"what project did it enter?"
"who commented?"
"what was beside it?"
"how was it ranked?"
        -> lost / fragmented
```

所以“档案保存到文件”不等于“保存到作品”。

## 11. 第二个机制：`community context has a larger dependency surface than the file`

一个 `.mid` 文件本身可能只需要：

- 一个静态 HTTP object；
- 几 KB / 几十 KB 存储；
- 不执行服务器逻辑。

但让它成为“FlontDoor 上的一首作品”还依赖：

- user/account table；
- submission record；
- title / description；
- category；
- index / search；
- comments；
- collaboration references；
- site navigation；
- software distribution context；
- community memory。

即：

```text
artifact dependency surface << cultural-identity dependency surface
```

这可以解释为什么旧网中经常出现：

> “文件还在，但已经没人知道它是什么。”

---

## 12. 第三个机制：避难所不是终点，而是一层新的保存依赖

FlontDoor 的迁移链还说明：

```text
original community failure
→ ad hoc refuge
→ refuge hosted on large free-homepage platform
→ host platform shutdown
→ partial archival rescue
```

因此 preservation path 本身也应建模：

```text
original host
!= emergency refuge
!= archive capture
!= later mirror
!= researcher reconstruction
```

每多一次迁移，就多一层：

- URL drift；
- metadata loss；
- file omission；
- encoding conversion；
- external-link rot；
- provenance ambiguity。

“避难所存在过”不能自动写成“原社区被完整保存”。

## 13. 已证实 / 高概率 / 不知道

### 已证实 / strong enough for current checkpoint

- 2005 的同期用户讨论把 `www.rukaf.net/flontdoor/` 直接作为 MIDIFlick 入口推荐；
- 2006-06-30 的参与者博客明确称 FlontDoor 已“消滅”，并说明自己建立避难所；
- Mixi 社区当前保存的旧文本把原站故障、长期掉线与 GeoCities 避难所 URL 联系起来；
- 后来参与者回忆明确描述 FlontDoor 的投稿、感想与合作作曲功能；
- Yahoo! GeoCities Japan 于 2019-03-31 结束服务；
- ArchiveTeam 把 GeoCities Japan 标为 partially saved。

### 高概率 / inference

- `/user/rop/` 很可能是某种用户 / 作品 namespace，但其精确语义未知；
- `kanashii` 很可能与“悲しい”这一词形有关，但不能据此确定正式曲名；
- 如果 Wayback locator 最终能直接打开并确认 payload，则它会给该文件的“最晚已存在时间”提供强约束，但不是创作日期。

### 不知道

- FlontDoor 精确成立日；
- 56,000+ MIDI 数字的原始统计出处；
- `rop` 的站内身份与现实身份；
- `kanashii.mid` 的显示标题、作者字段、首次投稿日、最后修改日；
- 文件内部是否有 title/copyright/text metadata；
- 原站作品索引是否还有其他 archive / mirror；
- 评论、评分、合作关系、排行、企划归属是否有幸存副本；
- 避难所保存了多少原站作品，还是主要承担用户重新聚集 / 软件信息功能；
- GeoCities Japan 抢救数据中是否包含该避难所的完整子树。

## 15. 对仓库的意义

FlontDoor 不是本仓的主地域对象，但它提供了一个很干净的比较框架：

> **数字保存的最小单位到底是什么？**

如果只把“一个 URL 返回了一个文件”视为成功保存，那么 `kanashii.mid` 也许已经“得救”。

但从文化史 / 社区史角度，它仍可能处在：

```text
bytes: survived
work identity: unknown
author identity: unknown
creation date: unknown
submission date: unknown
community context: mostly lost
```

因此本仓以后遇到旧网附件时，应避免只写：

> “资源仍可下载。”

还应继续问：

> **它作为一个“作品”的身份还剩多少？**

这正是 FlontDoor / `kanashii.mid` 作为比较样本最有价值的地方。
