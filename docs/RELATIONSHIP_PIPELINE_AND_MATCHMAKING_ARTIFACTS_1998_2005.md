# RELATIONSHIP_PIPELINE_AND_MATCHMAKING_ARTIFACTS_1998_2005.md

> 适用范围：约 1998–2005 年中文个人主页、聊天室、BBS、交友/婚恋网站及其相关帮助页、媒体记录和存档页面。
>
> 目标：防止把一个历史交友资料页、聊天室昵称、征友帖或婚恋网站账号，误读成一段完整的恋爱/婚姻事实。

## 1. 为什么需要单独建模

中文旧网中，交友、征友、网恋、婚介和早期婚恋站点很容易制造一种档案错觉：

> 页面上有一个“寻找对象”的人 → 这个人通过网站恋爱 → 线下见面 → 最后结婚。

但网页证据通常只能看见关系形成链条中的一小段。

1999 年一篇同时代第一人称上网经历就显示，普通网友关系可能经过：

```text
聊天室昵称
→ 持续聊天
→ Email / 电话 / 书信
→ 计划线下拜访
```

来源：
https://tech.sina.com.cn/news/internet/1999-8-4/3529.shtml

2000 年深圳婚姻介绍所建设“情网”的同期报道又显示，早期婚恋服务可以同时拥有线下机构和 Web 界面；网页并不必然是完整服务本体。

来源：
https://tech.sina.com.cn/news/internet-china/2000-04-29/24086.shtml

因此，本仓需要把**页面文物**与**关系生命周期**严格分开。

跨仓生活史分析见：
https://github.com/tmzncty/how-people-lived/blob/main/topics/mate-search-socialization-and-discovery-formation-decoupling-china-1986-2023.zh-CN.md

## 2. 核心规则：archived match artifact ≠ completed relationship

一个 archive capture 最多可以直接证明它所保存的窄事实，例如：

- 某 URL 在某 capture datetime 显示一个交友资料页；
- 页面存在“征友”“理想对象”“联系方式”等字段；
- 某聊天室/论坛帖子表达了想认识朋友或伴侣的意愿；
- 平台帮助页宣称用户可以搜索、发信、留言或交换联系方式；
- 某婚介机构当时确实运营一个 Web 入口。

它不能自动证明：

- 资料内容完全真实；
- 账号本人仍在使用；
- 有人实际联系过该用户；
- 双方后来交换电话；
- 发生过线下见面；
- 形成过恋爱关系；
- 以结婚为目的；
- 最后登记结婚或共同生活。

因此统一写成：

> **archived match artifact ≠ completed relationship**

并进一步区分：

> **relationship discovery evidence ≠ relationship outcome evidence**

## 3. relationship pipeline：把关系形成拆成不同证据阶段

建议旧网案例使用以下流程，而不是一个笼统的 `dating=yes`：

```text
discovery
→ initial interaction
→ repeated conversation
→ selective disclosure
→ off-platform handoff
→ identity verification
→ offline meeting
→ continued relationship
→ commitment
→ co-residence / marriage / household formation
```

每一阶段都需要自己的证据。

### 3.1 discovery

可由以下 artifact 支持：

- 搜索结果页；
- 交友目录；
- 用户资料页；
- 聊天室用户列表；
- BBS 征友帖；
- 婚恋网站分类页。

证明的是：

> 当时存在一个使用户彼此可发现的界面或公开自我陈述。

### 3.2 initial / repeated interaction

可能留下：

- 公开回帖；
- 留言簿；
- 聊天记录（极少可靠保存）；
- 平台公开消息板。

但大量私信、即时通信、Email 不会进入 Web archive。

### 3.3 selective disclosure

早期网络身份经常不是一次性公开真实姓名、单位、电话。

历史页面可能只显示：

- 昵称；
- 年龄/生日；
- 城市；
- 兴趣；
- 职业标签；
- 自我介绍。

随后才通过私聊交换：

- Email；
- 电话 / 手机 / BP；
- OICQ/QQ；
- 真实姓名；
- 单位/学校；
- 具体见面地点。

所以：

> **profile disclosure ≠ full identity disclosure**

### 3.4 off-platform handoff

一次关系可能从 Web 转移到：

- Email；
- OICQ/QQ；
- 电话；
- 手机短信；
- BP 机；
- 书信；
- 线下见面。

这与本仓现有 `CONTACT_STACK_AND_CHANNEL_HANDOFF_1998_2002.md` 直接相连。

必须记住：

> **web-originated or web-mediated relationship ≠ web-contained relationship**

### 3.5 offline meeting / commitment / marriage

这些阶段通常需要：

- 同时代第一人称；
- 独立新闻采访；
- 婚介机构记录；
- 当事人后来回忆（C 级，注明时间距离）；
- 其他可验证材料。

不能从资料页存在倒推。

## 4. “网恋”不是一个稳定的史料字段

2000–2002 年新闻已经大量使用“网恋”，但这个词可能覆盖非常不同的行为：

- 只在聊天室长期聊天；
- 双方互称恋人但从未见面；
- 已交换电话和真实信息；
- 已经线下见面；
- 普通异性网友被媒体重新命名成“网恋”；
- 已婚者在线形成另外的亲密关系。

2000 年中国新闻社一项选择性网络调查中，大量“有网恋倾向”的受访者尚未见面；这至少说明当时“网恋”并不天然等价于线下 dating。

来源：
https://news.sina.com.cn/society/2000-10-26/138345.html

2002 年四川青年网络生活调查又显示，聊天交友是主要用途之一，同时身份隐藏很常见；“是否真实身份”本身就是互动过程的一部分。

来源：
https://news.sohu.com/98/57/news204205798.shtml

因此考古记录应保存**原文术语**，同时另外编码行为阶段。例如：

```yaml
historical_term: 网恋
observed_behavior:
  repeated_online_conversation: yes
  exchanged_phone: unknown
  offline_meeting: unknown
  marriage_intent: unknown
researcher_normalization: online_intimacy_claim
```

不要用今天的 dating-app 分类法覆盖历史术语。

## 5. 平台字段只证明 schema，不证明用户人生

历史交友/婚恋站点常有字段：

- 婚姻状况；
- 年龄；
- 身高；
- 收入；
- 学历；
- 职业；
- 城市；
- 理想对象；
- BP/电话/Email/QQ；
- “是否愿意见面”。

### 规则 1

> **field exists ≠ field required**

页面模板出现一个字段，不代表所有用户必须填写。

### 规则 2

> **field filled ≠ field true**

尤其在匿名/半匿名平台，字段可能：

- 自报；
- 过期；
- 玩笑；
- 有意模糊；
- 平台默认值。

### 规则 3

> **current template ≠ historical template**

今天幸存页面使用的模板可能经过多年改版。一个账号注册于 2000 年，不代表当前页面上的所有 profile 字段在 2000 年已经存在。

应分别记录：

```yaml
account_created_at: 2000-??-??
profile_schema_observed_at: 2003-??-??
capture_datetime: 2005-??-??
```

不得把三者合并成一个“平台 2000 年功能”。

## 6. profile age 与 relationship age 必须分离

即使能证明一个资料页从 2001 年持续到 2004 年，也不能得出：

> 这个人从 2001 到 2004 一直单身/一直征友。

可能情况包括：

- 用户早已停止登录；
- 资料页没有自动下架；
- 用户已经恋爱但没有删除账号；
- 平台为了内容数量保留 inactive profile；
- archive 只保存旧版本；
- 域名或数据库迁移后恢复旧资料。

所以建议增加：

```yaml
profile_lifecycle:
  first_observed: ...
  last_observed: ...
  last_activity_observed: ...
  inactivity_policy_known: yes/no
  deletion_policy_known: yes/no
  relationship_status_current_at_capture: unknown
```

核心规则：

> **profile persistence ≠ availability persistence**

以及：

> **account lifetime ≠ relationship-status lifetime**

## 7. 婚介网站要拆开 institutional service 与 Web surface

2000 年深圳“情网”案例很适合说明这一点：报道中的主体是深圳市婚介所，同时存在 Web 站点、软件技术公司、旧域名/新域名和“网上免费交友”服务。

因此一个早期婚恋站不能只建：

```yaml
platform: 情网
```

至少需要：

```yaml
service_stack:
  offline_matchmaking_agency: yes/no/unknown
  web_directory: yes/no/unknown
  online_messaging: yes/no/unknown
  telephone_service: unknown
  staff_mediation: unknown
  offline_event: unknown
technical_operator: ...
institutional_operator: ...
domain_owner: ...
```

因为：

> **site operator ≠ institutional service provider ≠ technical contractor**

历史纠纷、域名变更或公司合作很容易把它们混在一起。

## 8. “成功率”是高风险历史指标

婚恋/交友平台特别喜欢出现：

- 成功率；
- 成婚对数；
- 注册会员数；
- 同时在线人数；
- 每日访问量；
- “促成多少姻缘”。

这些指标必须分别问：

1. 分母是什么？
2. `success` 指交换联系方式、见面、恋爱还是登记结婚？
3. 是平台自报还是独立统计？
4. 一个用户是否有多个账号？
5. inactive profile 是否仍计入会员？
6. 是否只统计主动反馈成功的人？
7. 新闻是否只是复述平台宣传稿？

2000 年一篇报道标题给出极低“网恋成功率”，但调查方法和 `success` 定义不足。因此本仓应把此类数字登记为：

```yaml
claim_type: reported_success_rate
source_claim: ...
metric_definition: unknown
sampling_frame: incomplete
confidence: low
```

而不是拿来做历史总体估计。

## 9. 身份可见性与核验：匿名不是“没有身份”

早期聊天室和交友网站常使用昵称，但匿名/化名并不意味着身份永远无法核验。

一种可能的历史流程是：

```text
nickname
→ repeated chat
→ city/school/work clues
→ email/QQ
→ phone
→ mutual friend / photo
→ offline meeting
```

每一步都可能增加身份可验证性。

因此不要做以下二元化：

```text
anonymous / real-name
```

更适合记录：

```yaml
identity_visibility:
  public_profile: pseudonymous
  location_disclosed: yes
  email_disclosed: private/unknown
  phone_disclosed: later/unknown
  offline_identity_verified: unknown
```

这与本仓已有 `SOCIAL_STATUS_VISIBILITY_AND_CONSUMER_ACCOUNT_IDENTITY_2008_2010.md` 的原则一致：

> 平台没有显示某个现实身份，不等于现实身份不存在。

## 10. 关系流程存在强烈 archive asymmetry

Web archive 最容易保存：

- 公共 profile；
- 征友帖；
- 论坛公开回复；
- 站点首页；
- 平台帮助页；
- 公开统计/宣传；
- 新闻报道。

最容易丢失：

- 私信；
- 聊天室实时内容；
- Email；
- QQ/OICQ 对话；
- 电话；
- 短信；
- BP 寻呼；
- 线下见面；
- 婚介工作人员的人工撮合；
- 用户自己删除的关系历史。

于是档案会系统性制造一种错觉：

> “关系最重要的部分发生在公开网页上。”

实际上公开网页很可能只是 `discovery surface`。

统一规则：

> **archived discovery surface ≠ social relationship graph**

以及：

> **archive density is highest near public beginnings, not necessarily near private maintenance。**

## 11. ghost profile：旧资料页可能保存的是“已经结束的可发现性”

婚恋/交友站特别需要记录一种对象：**ghost profile（幽灵资料页）**。

定义不是“假账号”，而是：

> 页面仍可访问/被 archive 保存，但无法证明账号在该时点仍由用户积极维护或仍代表当时的交友意愿。

判断线索包括：

- 最后登录时间；
- 最后更新；
- 平台 inactivity policy；
- 是否显示已注销；
- 搜索列表是否仍返回；
- 页面是否来自 archive 旧 capture；
- 是否有后续活动。

不得由 `profile URL returns 200` 推断 `user was actively seeking partner`。

---

## 12. rehosting / reposting：个人资料也可能脱离原平台继续存活

旧网中个人资料可能被：

- 搜索引擎缓存；
- 门户转载；
- 镜像；
- 平台改版迁移；
- 合作站点 syndication；
- 论坛用户引用/截图。

因此：

> **profile found on host B ≠ user registered on host B**

需要记录：

```yaml
artifact_origin:
  original_platform: unknown/...
  observed_host: ...
  repost_or_syndication: yes/no/unknown
  first_observed_at: ...
  source_link_preserved: yes/no
```

尤其不要因为某资料在 2004 年 portal B 上被发现，就把账号创建时间写成 2004。

## 14. 隐私：婚恋文物必须比普通站点更保守

此类页面经常含：

- 真实姓名；
- 出生日期；
- 电话；
- BP 号码；
- Email；
- 工作单位；
- 身高、收入、婚史；
- 照片；
- 性偏好/伴侣偏好；
- 家庭情况。

这些信息即使仍在 archive 中，也不代表本仓应该重新聚合传播。

### 最低规则

- 普通个人联系方式默认不复制进仓库；
- 不建立“历史单身人士数据库”；
- 不把 profile 跨站点重新做实名归并，除非研究上不可替代且属于明确公共人物；
- 研究字段形态时优先抽象 schema，而不是保留具体个人值；
- 需要引用个案时只保留支持 claim 的最少信息；
- 不利用今天的数据反查普通人的历史婚恋账号真实身份。

## 15. 海外比较只作为机制校验，不扩大本仓 scope

1986 年法国 Minitel 的同时代报道已经显示：数百万终端环境中，用户可以用化名和简短自我介绍进入消息/约会服务，随后在交换电话号码时逐渐退出匿名状态。

来源：
https://www.washingtonpost.com/archive/politics/1986/12/25/minitel-is-new-french-revolution/eeaf90f3-90ca-4d60-bb46-fc4808fa2649/

它说明：

> `pseudonymous discovery → interaction → phone handoff`

是前 Web 交互式网络也可以产生的共同机制。

**但这不是把本仓扩成法国/Minitel 历史库。** Minitel 的完整生活史比较应放在 `how-people-lived`；本文件只用它检验“中文 Web 的关系流程是否属于 Web 独有机制”。

中文旧网需要研究的仍是：

- 哪些中文站点提供哪些字段；
- 页面/账号如何保存；
- OICQ/QQ/Email/电话如何接走关系；
- 婚介机构与技术运营方如何分工；
- Web archive 为什么只保存关系的公开边缘。

## 16. 最小 claim 模板

### 好的写法

> 2000-04-29 的同期报道表明，深圳市婚介所运营的新版“情网”提供网上免费交友服务；报道同时显示婚介机构、网站域名和技术公司属于同一服务史中的不同主体。

### 不好的写法

> 2000 年深圳年轻人已经普遍通过网站找对象。

---

### 好的写法

> 某 2002 capture 中，一个交友 profile 公开显示昵称、城市和征友文字。

### 不好的写法

> 该用户 2002 年单身并正在积极寻找配偶。

---

### 好的写法

> 同时代第一人称材料证明，1999 年部分联网用户已把聊天室关系转到 Email、电话和书信等渠道。

### 不好的写法

> 1999 年网民普遍通过聊天室发展线下恋爱。

## 17. 本规则新增的考古结论

过去容易把旧网婚恋/交友研究做成“平台清单”：

```text
某网站何时上线
有多少会员
有什么 profile 字段
```

本规则要求进一步恢复**关系流程与档案断面之间的差别**：

> 一个页面首先是关系形成过程中某个时点留下的 artifact，而不是这个人的完整感情生活。

中文旧网的历史可见性因此有明显方向性：

> **公开的“我想认识谁”比私下的“我们后来怎样相处”更容易被保存。**

如果忽略这个偏差，研究者会系统性高估平台公开界面对关系生活的占比，并把那些没有进入网页、只发生在单位、朋友、电话、书信和线下空间里的关系错误地写成“不存在”。
