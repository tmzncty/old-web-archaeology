# 家政服务 Profile、混合匹配与入户执行缺口（2005–2010）

> 状态：bounded research note；**不是 M1 完整案例**。
>
> 主体范围：2005–2010 中文旧网中与家政 / 保姆 / 钟点工匹配有关的网站栏目、在线预定、可浏览劳动者 profile、社区论坛与 Web→电话→线下的 handoff。
>
> 边界：1990s 社区家政服务只作为“Web 不是起点”的前史说明；2014 以后 App / O2O / 信用平台不属于本篇主体。
>
> 研究问题：**当一名家政服务员出现在网页上时，这个页面到底证明了什么？从“看见一个 profile”到“这个人真正走进某户家庭并持续工作”，中间哪些状态会离开公开 Web，因此几乎不可能被 archive 完整保存？**

---

## 0. 为什么这个对象值得单独研究

本仓已经处理过：

- 招聘 listing 与申请结果；
- roommate / 租房 listing 与共同居住结果；
- 婚恋 profile 与 mutual-selection funnel；
- 二手 listing 与交易结果；
- 在线教育 account / courseware / progress；
- 医院预约 portal 与动态号源；
- contact handoff 与 QQ / 电话等私有终端。

家政看起来像“又一种 classifieds”，但它有几个不能由普通招聘 / 租房模型直接替代的特征：

1. **服务对象是人，不是商品或普通岗位字段**；
2. **工作场所是私人家庭**；
3. **匹配后需要长期、重复、近距离进入家庭空间**；
4. **“适不适合”包含很多无法稳定字段化的生活习惯与信任判断**；
5. **劳动关系可能是家庭直接雇佣、中介介绍、企业管理或多种混合形态**；
6. **真正的工作过程天然不应成为公开 Web artifact**。

因此家政旧网最适合建立一个 **profile-to-household execution archaeology**。

---

## 1. 研究单位

按照 `docs/METHOD.md`，本篇至少分开：

### platform / site

家政公司网站、地方社区网站、门户家政栏目、社区论坛。

### category / service page

例如：

- 保姆推荐；
- 钟点工；
- 育儿 / 护老；
- 涉外家政；
- 家政需求 / 求雇信息。

### worker profile

某位家政服务员的公开介绍。

可能包含：

- 照片；
- 年龄；
- 籍贯；
- 学历；
- 技能；
- 证书；
- 星级；
- 经验；
- 工资区间；
- 当前状态。

### household demand post

雇主或社区居民发布的需求。

### reservation / inquiry

网上预定、在线表单、站内咨询。

### contact endpoint

电话、QQ、Email、门店地址、后来的 IM。

### match

双方认为可以继续谈。

### household entry

劳动者真正进入家庭开始服务。

### service relationship

工作持续、调整、续约、辞工、更换、结束。

### capture

archive / 搜索引擎 / 仍存活页面保存的某个时点 artifact。

硬规则：

> **profile 是 artifact；household service relationship 是 event / process。两者不能混写。**

# 第一部分：前史边界——Web 没有发明家政匹配

## 3. 1998 武汉：人工走访已经能做双边供需匹配

1998 年 12 月 5 日《人民日报》报道武汉万松园街家政服务试点。市 / 区妇联与街道工作人员骑自行车逐户调查，用两天摸清有服务需求的家庭和愿意从事家政的女工；服务队成立当天上午即有 20 多户家庭签约聘用钟点工。

数字化报道：

<https://cn.govopendata.com/renminribao/1998/12/05/7/>

### 证据等级

**B：同期报纸数字转录。**

### 对本仓的边界意义

它证明在大众家庭 Web 普及前，城市社区已经可能拥有：

```text
需求发现
+ 劳动者名册
+ 人工匹配
+ 信任中介
+ 合同 / 入户
```

所以 2005 以后中文 Web 的问题不是“家政匹配第一次出现”，而是：

> **哪些原本由街道、家政中介、电话和线下名册执行的操作，被公开页面和用户自助检索部分接管。**

本篇不把 1998 扩展成旧网主对象，只将其作为必要前史边界。

# 第二部分：2005，中文 Web 进入一条原本已经存在的混合渠道

## 4. 2005-07：网上预定不是端到端在线雇佣

2005 年 7 月 21 日《北京晨报》回答读者“如何预定川妹子保姆”时，明确写出：

- 网上预定；
- 电话咨询；
- 现场挑选。

报道还提供了：

```text
www.chuanmeizi.com.cn
www.awjz.com
```

来源：

<https://news.sina.com.cn/c/2005-07-21/04106487323s.shtml>

### 证据等级

**B：同期媒体。**

### 4.1 网站是入口之一，不是完整执行环境

当前最小可支持的历史模型是：

```text
news / web page
→ online reservation OR phone inquiry OR on-site selection
→ candidate information
→ interview / negotiation
→ agreement
→ household entry
```

因此固定：

> **online reservation ≠ online hiring**

以及：

> **website existed ≠ household could complete the whole process in browser**

### 4.2 candidate archive targets

`chuanmeizi.com.cn` 与 `awjz.com` 是由 2005 同期报道给出的历史 locator。

本轮没有在可可靠核验的 archive 回放中确认：

- 2005-07 当日首页；
- 预定表单具体字段；
- form action；
- 是否需登录；
- 是否有 worker profile；
- 提交后进入何种 backend。

因此它们只能登记为 **historical candidate URLs**，不能在本篇伪装成已检查的 A 级 capture。

---

## 5. 2005-01：公开网页价格可能已经过期

2005 年 1 月 13 日北京现代商报报道，记者在网上查看数家北京家政公司页面时，价格项目仍写普通家政服务月薪 600–800 元；随后记者打电话询问，得到的回答却是市场已经涨价，具体工资需要雇主与服务员协商。

来源：

<https://finance.sina.com.cn/roll/20050113/00001289970.shtml>

### 证据等级

**B：同期媒体对网页 + 电话的双通道观察。**

### 5.1 published-price freshness gap

增加 **published-price freshness gap（公开价格新鲜度缺口）**：

```text
HTML price table at t0
≠ telephone quote at t1
≠ negotiated wage at t2
≠ actual paid wage at t3
```

在春节、供需波动或岗位任务差异很大的市场中，这几个状态甚至可能在几天内明显不同。

因此历史网页上的工资只能写成：

> “该页面在该时点公开标示这一价格 / 区间。”

不能直接写成：

> “当时家政员的实际工资就是这一数字。”

# 第三部分：2006，劳动者变成可浏览 profile

## 6. “文晖新干线”的保姆推荐栏目

2006 年 1 月 17 日，浙江在线记者写道，自己登录杭州下城区“文晖新干线”，发现网站新增“保姆推荐”栏目；页面中能看到“明星保姆”“星级保姆”等照片和介绍。

报道还描述一家达盟家政公司使用星级系统，把不同家务 / 护理经验与公开工资档位关联起来。

来源：

<https://zjnews.zjol.com.cn/05zjnews/system/2006/01/17/006446359.shtml>

### 证据等级

**B：同期记者对网页的直接观察。**

这是比后来回忆强得多的 evidence，但仍然不是历史 HTML / capture 本身。

---

## 7. profile schema：页面开始把人拆成字段

根据同期报道，当时的家政 profile 至少可能强调：

- 头像 / 照片；
- 学历；
- 语言；
- 职业经历；
- 证书；
- 家务或护理能力；
- 星级；
- 工资范围。

这非常适合和本仓已有的：

- dating profile；
- job résumé；
- roommate ad；

做结构比较。

但家政 profile 有一个更强的后果：

> 用户不是只决定“要不要聊天 / 面试”，而是可能决定让这个人长期进入自己的住宅。

所以 profile 是一种 **pre-entry trust interface**。

---

## 8. worker-profile state gap

一个 profile 可能持续显示：

```text
姓名 / 昵称
照片
星级
期望工资
技能
证书
```

但真正决定“现在能不能雇”的字段可能在 backend：

- 待岗；
- 已上户；
- 休假；
- 已签约；
- 只接某类订单；
- 只去某地区；
- 春节回乡；
- 已退出平台。

因此新增：

> **worker-profile state gap**

硬规则：

```text
profile survived
≠ worker was available at capture time
```

如果公开页面只保留静态简介，而 availability 由门店 / 数据库 / 电话实时维护，archive 会系统性高估“可雇库存”。

---

## 9. mutable-profile time collapse

家政 profile 还可能长期更新：

```text
2006 新手
→ 2007 有育儿经验
→ 2008 工资提高
→ 2009 已有更多证书 / 评价
```

如果 archive 只保存最后一版，今天很容易把后来的经验、星级和工资倒投到早期。

因此沿用本仓已有 **mutable-profile time collapse** 原则，并在家政场景明确：

> **current/later profile state ≠ historical worker state**

尤其要避免：

- 把现在的证书数量写进早期履历；
- 把后来积累的五星评价当成首次上网时已有；
- 把后来工资倒投到原始 posting date。

---

## 10. credential-field gap

2006 报道中的高学历、外语、资格证等字段说明平台和公司希望用 credentials 提高可读性。

但必须固定：

```text
credential listed
≠ credential independently verified
≠ relevant domestic-service skill verified
≠ employer-worker fit verified
```

这和 `CREDENTIAL_QUERIES_DYNAMIC_DATABASES_AND_PERSONNEL_RECORD_GAPS_2001_2010.md` 可以交叉，但本篇关注的是：

> **credential 如何成为“允许陌生人进入家庭”之前的信任字段之一。**

# 第四部分：2007，社区论坛不只匹配 worker，也匹配 household

## 11. 回龙观社区网的“合雇 / 拼保姆”

2007 年 5 月 17 日，中国经济网报道：记者在回龙观社区网亲子论坛搜索“合雇保姆”或“拼保姆”，能找到最近数个帖子。

其中一个用户的需求是：孩子 3 个月大，希望找不住家保姆，只覆盖每周一、三、四白天，并寻找有相似需求的邻居共同雇佣。

来源：

<https://finance.ce.cn/xf/main/zx/200705/17/t20070517_11388894.shtml>

### 证据等级

**B：同期媒体对论坛帖子存在与内容的观察。**

本仓按隐私最小化原则，不需要重新发布普通用户旧联系方式，也不需要围绕 ID 做人格化追踪。

---

## 12. demand-side matching

这个案例揭示了一类与普通招聘平台不同的 old-web interaction：

```text
household A has partial-time demand
household B has complementary demand
→ forum lets A discover B
→ both may share one worker
```

即：

> **网站不只在 worker ↔ employer 之间匹配，也能在 employer ↔ employer 之间匹配。**

这属于 **demand-side matching（需求侧匹配）**。

社区论坛尤其适合这种行为，因为它同时提供：

- 地理接近；
- 同一小区 / 社区 namespace；
- 育儿主题共同兴趣；
- 可公开发帖；
- 后续转电话 / QQ / 线下的入口。

---

## 13. shared-service outcome gap

但公开帖子只证明：

> 有人提出了共同雇佣的愿望。

它不能证明：

- 找到了第二户家庭；
- 找到同一位保姆；
- 时间表协调成功；
- 工资怎么分；
- 责任怎么分；
- 实际持续了多久。

于是增加：

> **shared-service outcome gap**

硬边界：

```text
co-hire post
≠ co-hire arrangement formed
≠ worker accepted the schedule
≠ arrangement persisted
```

真正执行最可能转向：

- 站内私信；
- QQ；
- 电话；
- 小区见面；
- 家中面谈。

这些状态天然很难进入公共 Web archive。

# 第五部分：家政 old-web execution state machine

## 14. worker-side state machine

建议以后对家政网站按以下状态拆解：

```text
worker exists
→ registers / contacts agency
→ training / credential collection
→ profile created
→ profile published
→ available for matching
→ employer discovers profile
→ inquiry / reservation
→ interview
→ wage / duty / schedule negotiation
→ agreement / contract
→ household entry
→ trial / adjustment
→ continuing service
→ renewal / termination
→ re-listing / reassignment / exit
```

公开 Web 最容易保存：

```text
profile published
```

而历史上最重要的后续状态恰恰最难保存。

---

## 15. household-side state machine

家庭侧则是：

```text
care / housework gap appears
→ decide whether family can cover it
→ decide paid help is needed
→ choose channel
→ search / ask / call / visit
→ inspect profiles / shortlist
→ verify identity / skill / references
→ interview
→ negotiate price / scope / hours / live-in status
→ agree
→ worker enters home
→ trial
→ routine work
→ renegotiation / conflict / leave / replacement
```

因此必须新增硬规则：

```text
service page exists ≠ household searched it
profile viewed ≠ inquiry
inquiry ≠ interview
interview ≠ match
match ≠ agreement
agreement ≠ household entry
household entry ≠ durable employment
```

# 第六部分：几类特殊 archive gap

## 16. household-entry gap

这是本篇最关键的新 gap。

一份家政关系真正开始的时刻是：

> **服务员进入家庭并开始劳动。**

但这一步：

- 没有必要公开；
- 涉及家庭住址与隐私；
- 往往由电话、合同或线下协调；
- archive 不应追求完整保存。

因此：

> **household-entry gap 是结构性且常常合理的隐私缺口。**

不能把“archive 没有入户证据”当成站点保存失败，也不能为了补洞去寻找泄露的住址、合同或私人聊天。

---

## 17. service-duration gap

就算能够证明开始上户，也通常不知道：

- 做了 1 天；
- 5 天磨合后结束；
- 做了 3 个月；
- 连续照顾一个孩子 3 年。

因此：

> **start-of-service ≠ duration**

家政页面特别容易把劳动关系压缩成一个“当前状态”，却抹掉真实时间长度。

---

## 18. duty-topology gap

“保姆”不是一个足够精确的历史单位。

同一个 label 可能指：

- 单纯清洁；
- 做饭；
- 育儿；
- 护老；
- 陪伴；
- 接送孩子；
- 住家；
- 不住家；
- 若干任务同时承担。

因此增加：

> **service label ≠ duty topology**

如果旧页面只剩 category 名称，不能由“保姆”两个字推断具体工时、责任和生活状态。

---

## 19. wage-state gap

工资至少要区分：

```text
published price / guide price
advertised expectation
telephone quote
negotiated wage
actual cash / bank payment
holiday premium / bonus
```

2005 网站价与电话价不同已经直接证明这些状态不能合并。

如果历史页面只保存一个“600–800”，就不能把它当成真实 household transaction price。

---

## 20. agency-role ambiguity

家政网页上的公司 logo 也不能自动回答：

> **这家公司是不是劳动者的 employer？**

可能存在：

```text
information listing only
intermediary introduction
training + referral
management agreement
employee-based service
three-party agreement
```

因此：

> **agency page ≠ agency employment relationship**

这对旧网考古尤其重要，因为公司页面往往是最容易保存的 artifact，而真正劳动关系可能在合同数据库或线下。

---

## 21. trust-field survival bias

家政网站倾向保存最适合展示的 trust fields：

- 学历；
- 证书；
- 星级；
- 照片；
- 公司保障；
- 推荐语。

但不容易保存：

- 被拒绝的候选人；
- 雇主真正为什么更换人；
- 服务员为什么不接某一户；
- 家庭内部的边界冲突；
- 工作强度与休息；
- 一次短暂匹配为什么结束。

因此 archive 可能系统性高估“可展示的专业性”，低估 **fit negotiation**。

---

# 第七部分：与其他旧网对象的比较

## 22. 与 job board 的不同

job board 常见：

```text
job → application → interview → employment
```

家政则多了一层私人空间：

```text
service demand
→ candidate
→ interview
→ agreement
→ physical household entry
→ repeated intimate co-presence
```

所以普通招聘中的“录用”不能完全替代家政的“上户”。

---

## 23. 与 dating profile 的相似与不同

相似点：

- profile 字段化；
- 双方都在挑选；
- first contact 不代表后续关系；
- household fit 很难由字段预测。

不同点：

- 家政有明确的有偿劳动与职责；
- 工资、工时、保险 / 合同是核心；
- 家庭地址与进入权限构成执行条件。

所以可以借用 reciprocal selection，但不能把劳动关系浪漫化成“看眼缘”。

---

## 24. 与 roommate ad 的相似与不同

相似点：

- 都让陌生人进入私人居住空间；
- 地理距离强；
- 生活习惯与安全判断重要；
- 真实关系在公开网页外发生。

不同点：

- roommate 共享住房；
- 家政员是在住宅内提供有偿劳动；
- 住家家政甚至把住房、工作和休息进一步叠在一起。

---

# 第八部分：browser / encoding / archival checklist

## 25. 如果以后取得 2005–2007 原始家政页面，应记录什么

### 页面层

- original URL；
- capture datetime；
- title；
- charset / Content-Type；
- table / frameset；
- 图片 URL；
- profile URL pattern；
- pagination；
- query params；
- 是否静态 HTML / ASP / JSP / PHP；
- 是否登录后才可见更多字段。

### profile 层

- profile ID 是否稳定；
- 照片是否独立资源；
- availability 是否公开字段；
- 工资是固定字段还是文字描述；
- 星级由谁决定；
- 证书字段是否只是自报；
- “已上户 / 待岗”等状态是否随时间覆盖。

### handoff 层

- 是否公开电话；
- 是否 QQ / Email；
- 是否存在在线预定 form；
- form action 指向哪里；
- 是否产生公开结果页；
- 是否只返回“客服会联系”；
- 是否要求用户去实体门店。

### 浏览器层

2005–2007 页面若涉及：

- IE-specific JS；
- ActiveX；
- GB2312 / GBK；
- table layout；
- Flash；
- popup / modal；

必须记录历史浏览环境假设。

现代浏览器能显示新闻描述或残存 HTML，不等于历史预定流程仍可执行。

---

# 第九部分：隐私与伦理 stop conditions

## 26. 家政 profile 的隐私风险高于一般商品 listing

普通家政员 profile 可能包含：

- 姓名；
- 照片；
- 籍贯；
- 年龄；
- 电话；
- 家庭状况；
- 身份证 / 证书线索；
- 工作经历。

即使 2006 年曾公开，也不意味着 2026 年应该把删除内容批量重新公开。

因此本仓只需要：

- 保存平台 / 栏目结构；
- 记录字段 schema；
- 在确有必要时使用最少量的同期公开例子；
- 不建立普通家政员可搜索的人名数据库；
- 不重新发布历史电话、住址、身份证等敏感信息。

---

## 27. household side 同样应最小化

论坛“拼保姆”帖子可能泄露：

- 婴儿年龄；
- 小区；
- 家庭作息；
- 联系方式。

研究需要的是：

```text
partial-time demand
+ shared hiring intention
+ community forum as matcher
```

而不是恢复这个家庭今天是谁。

所以：

> **relationship archaeology must not become doxxing.**

---

# 第十部分：已证实 / 高概率 / 不知道

## 28. 已证实

- 2005 同期新闻明确把“网上预定、电话咨询、现场挑选”并列为家政选择入口；
- 2005 同期记者观察到网站公开工资与电话实时询价不一致；
- 2006 同期记者观察到地方网站的“保姆推荐”栏目包含照片 / 简介 / 星级；
- 2007 同期媒体观察到社区论坛上存在合雇 / 拼保姆需求；
- Web 在这一时期已经进入家政 matching，但公开证据同时反复显示电话、门店、面谈与入户仍是执行链的重要部分。

---

## 29. 高概率但需要原始 capture 才能进一步确认

- 一些 2005 家政网站可能存在在线预约 form；
- 2006 “保姆推荐”可能由动态数据库生成；
- worker availability 可能在公司内部系统中维护而不完全公开；
- profile 的照片、星级、工资与状态很可能随时间更新。

这些都必须等 capture / HTML / historical screenshot 才能升级。

---

## 30. 目前不知道

- `chuanmeizi.com.cn` 在 2005-07 的具体页面结构；
- `awjz.com` 当时是否有公开 worker profile；
- “文晖新干线”保姆栏目真实 URL pattern；
- 页面是否可被搜索引擎完整索引；
- 某个 worker profile 在被雇后多久更新 / 删除；
- 网上预定后平均多久电话回访；
- 2007 拼保姆帖子有多少真正形成共享雇佣；
- 公开 Web 上的“星级”是否有明确可复核评分规则。

这些不知道应保留，不用 D 级 reconstruction 补全。

# 第十一部分：下一步 archive research package

## 31. 优先 locator

如果下一轮继续这一对象，优先验证：

```text
chuanmeizi.com.cn (2005)
awjz.com (2005)
文晖新干线 / 下城区相关历史 host (2006)
回龙观社区网亲子论坛相关 2007 板块
```

目标不是批量抓 profile，而是找到：

- 至少两个历史时点；
- category page；
- 一个经过隐私最小化的 profile schema；
- 一个 reservation / inquiry flow；
- 一次明显的 Web→电话 / 门店 handoff。

---

## 32. 最值得证明的一条链

理想的旧网证据链是：

```text
2005/2006 service category capture
→ worker profile capture
→ reservation / contact interface
→ contemporaneous user / media evidence of phone or in-person interview
→ later profile state change / disappearance
```

如果能做到，就可以第一次较可靠地回答：

> **中文 Web 早期究竟只是把“家政公司电话号码”搬上网，还是已经开始维护一套可搜索、可变状态的劳动力库存。**
