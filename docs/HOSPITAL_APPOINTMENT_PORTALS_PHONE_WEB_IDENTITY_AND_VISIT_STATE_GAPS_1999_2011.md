# 医院预约挂号门户、电话/Web 协同与现实就诊：1999–2011 中文旧网的 identity / slot / visit state gaps

> 研究对象：约 1999–2011 年中国、尤其北京的医院预约挂号 Web / 电话平台。本文不是医院史，而是回答：**一张网上挂号页、一条“预约成功”记录，究竟能证明现实就诊链中的哪一步？**

生活史对应研究：

- `tmzncty/how-people-lived/topics/hospital-appointment-care-routing-proxy-labor-and-medical-access-china-1953-2024.zh-CN.md`

本文件严格保持本仓约 1995–2015 中文旧网 scope。1950s 电话预约、1993 院内计算机预约只作为理解 1999 年以后 Web 预约的必要前史，不把仓库扩成一般医疗史。

---

## 1. 先固定研究单位：appointment page 不是 medical visit

医院预约旧网至少要区分：

- **institution**：医院、卫生行政部门、电话运营商；
- **platform/service**：某“一卡通”、医院自有预约系统、114 统一预约平台；
- **site/host**：如历史上的 `www.bjguahao.gov.cn`；
- **page/form**：注册、医院列表、科室列表、预约表单、帮助页；
- **account / patient identity**：预约账号、身份证件、手机号、医院就诊卡；
- **doctor / department schedule**：现实出诊安排；
- **slot inventory**：某一时刻可预约号源；
- **reservation state**：请求、锁号、确认、取消、爽约；
- **hospital HIS state**：医院内部挂号/就诊系统中的记录；
- **check-in / visit state**：现场核验、取号、候诊、实际见医生；
- **capture/artifact**：档案或新闻保留的一次页面/流程表示；
- **claim**：研究者能安全作出的最小陈述。

因此必须固定：

> **`page survived ≠ backend survived ≠ slot existed at capture time ≠ reservation succeeded ≠ patient was seen`**

医疗 Web 比一般资讯站更像“过程型 Web”：公共页面只暴露流程壳，决定现实结果的大量状态在医院后台、短信、电话和现场系统里。

## 2. 1999：网上挂号已经存在，但不能从后来回顾复原 1999 页面

《北京日报》2020 年基于其历史图文数据库回顾称，1999-09 北京“网上挂号”服务开通，持“北京市医院预约挂号一卡通”者可通过当时的“北京卫生信息网”预约最初 18 家医院，后来增加到 24 家；同一张卡也可电话预约。[1]

2006 年《人民日报》回顾该系统时称，1999 年以来后来已有 50 多家医院加入，并记录卡费、预约次数和电话/Web 双入口。[2]

这两组证据足以支持窄 claim：

> **1999 年北京确有面向患者的电话 + Web 远程预约挂号服务。**

但本轮没有可靠恢复：

- “北京卫生信息网”当年预约入口的 original URL；
- 1999 年注册/登录/选医院表单的 A 级 capture；
- 当年 HTML、frameset、JS、charset；
- 浏览器版本、cookie/session 要求；
- “一卡通”与 Web 账号的具体绑定协议；
- 医院端实时号源同步机制。

因此：

> **不能把 2020 年新闻里的历史描述反绘成 1999 Web UI。**

这是典型的 `service-exists / original-artifact gap`。

### Internet 时间边界

中国在 1994-04-20 实现全功能接入国际互联网，但官方历史回顾明确保留此前学术联网等前史；1998 年底 CNNIC 统计上网用户约 210 万。[3][4]

所以 1999 网上挂号应该描述为**早期公众网络服务**，而不是“大众家庭已经普遍网上就医”。电话入口在当时尤其不能被当成 Web 的附属品。

## 3. 2006：一个平台页面不能证明“热门专家号”真的进入它的库存

2006-01-19《人民日报》同期调查指出，北京预约挂号“一卡通”虽然可电话和网上预约，但最紧俏医院/专家的号源并没有充分进入统一系统；有的专家每天只给“一卡通”1–2个号，一些医院还有自己独立的预约卡和独立系统。[2]

因此新增：

### `inventory-partition gap`

同一个医生现实中可出诊的号源，可能被拆给：

```text
现场窗口
+ 医院自有卡
+ 市级一卡通
+ 电话
+ Web
+ 复诊工作站
+ 社区转诊
+ 特需/其他渠道
```

网页写着“支持某医院/科室”，不等于该医生的全部号源进入此平台。

进一步：

`doctor on roster ≠ doctor has platform slots`。

### `hot-slot representativeness gap`

一个平台可能大量提供普通号，却对“最难挂”的专家只提供极少份额。不能用总预约量推断紧俏资源的可获得性。

## 4. 2009：国家制度要求是 A 级，但 local state 仍需另证

2009-09-30，卫生部正式发布《关于在公立医院施行预约诊疗服务工作的意见》，要求从 2009 年 11 月起所有三级公立医院开展预约诊疗，并要求定期更新科室、医生专长和出诊时间。[5]

这是 **A 级机构制度证据**，能证明全国性政策要求。

它不能自动证明：

- 某医院哪一天技术上线；
- 电话是否打得通；
- Web 是否可用；
- 具体医生是否有号；
- 号源更新是否实时；
- 某位患者是否完成就诊。

因此固定：

> `policy exists ≠ local service online ≠ slot accessible ≠ patient used it`。

## 5. 2009 的电话预约说明：公开“号码列表”仍不是可执行服务

2009 年北京推进三级医院预约时，同期报道已经发现部分医院预约电话持续占线或无法接通，有的患者即使打通电话，也因为没有预先办理医院诊疗卡而无法继续。[1]

这产生两个很重要的 Web/电话 archaeology gaps：

### `contactability gap`

历史网页保存一个预约电话号码，只能证明平台**公布了这个入口**。

它不能证明当时：

- 坐席开放；
- 线路未拥塞；
- 用户在放号窗口拨得进去；
- 号码没有改；
- 夜间与白天规则一致。

### `prerequisite-card gap`

公开帮助页可能只写“电话预约”，实际执行却要求先到医院建立就诊卡/诊疗档案。

于是：

`remote channel advertised ≠ first-time patient can execute remotely`。

这类前置条件特别容易从 archive 中丢失，因为它可能写在医院单独页面、纸质卡说明或客服口头流程里。

## 6. 2011 统一平台：第一次可以较完整地重建 public-side state machine

2011-07-28，北京启动 114 统一预约挂号平台；卫生部次日的正式材料说，首批 30 家三级医院已经完成内部系统改造，与统一平台建立号源数据交互机制。平台以一个电话号码与一个网站向公众服务。[6]

同期《北京日报》留下相当清楚的 Web/电话操作流程：[7]

```text
首次注册 / 登录
→ 选择医院、科室
→ 选择日期/医生层级
→ 填预约信息
→ 短信验证
→ 后台确认
→ 短信/电话返回预约成功信息
→ 获得 8 位识别码
→ 就诊日携身份证/就诊卡到医院
→ 现场取号/就诊
```

这已经足够把 2011 预约站看成一个跨系统状态机，而不是静态网页。

### public side 和 hospital side 之间有一条明确 seam

卫生部材料还说明 30 家医院进行了内部系统改造并建立号源数据交互。[6]

因此 Web 考古至少必须区分：

```text
browser/session state
→ unified platform reservation state
→ platform ↔ hospital inventory synchronization
→ hospital HIS registration state
→ on-site identity/check-in state
```

一张“预约成功”页面只处于中间，不是终点。

## 7. 身份不是一个字段，而是一条跨系统一致性约束

2011 同期体验报道说，首次电话预约需要提供真实姓名、身份证号码、手机号和报销方式，成功后获得 8 位识别码；就诊时要带身份证和就诊卡。[8]

北京妇产医院 2011 年官方材料又说明，平台改造前初诊者往往需要先到医院建卡/关联社保卡，改造后可先在家用实名信息预约，再在就诊日到院建卡或关联。[9]

因此新增：

### `identity-binding gap`

至少有：

- 预约平台注册身份；
- 有效身份证件；
- 手机号；
- 医院就诊卡/医联码；
- 社保/报销信息；
- 现场持证人。

历史页面里显示“姓名 + 身份证号”字段，不足以说明这些身份对象怎样映射。

### `same-person enforcement gap`

`account holder ≠ patient ≠ booking operator ≠ companion`。

尤其家属代预约时，实际操作人和患者可能不同；系统却可能要求患者本人证件最终在现场出现。

研究时不要把“谁点了网页”自动当作“谁去看病”。

## 8. slot 是时间函数：单个 capture 很容易造成历史时间坍缩

统一平台上线后，医院放号时间并不完全相同。2011 同期报道说相当多医院集中在早晨放号，也有少数下午放号；紧俏专家号可很快约满。[8][10]

这产生：

### `slot-snapshot gap`

一份 08:29 的 capture 和 08:31 的 capture 可能看到完全不同的库存。

因此：

> **slot inventory 必须带时间戳理解，不能把某次页面快照当成整日“有没有号”的证据。**

### `release-time queue gap`

物理排队可以被移到：

- 电话等待音乐；
- 网页刷新；
- 登录 session；
- 放号时刻；
- 短信验证；
- 最终提交竞争。

“网上没有排队照片”不等于没有 queue。

## 9. appointment success 仍不是 visit success

2011 流程里至少还存在：[7][8]

```text
预约成功
→ 获得识别码
→ 等到就诊日
→ 按规定时间到院
→ 身份核验
→ 取号/签到
→ 候诊
→ 医生实际出诊
→ 实际就诊
```

因此新增：

### `appointment-lock gap`

页面显示号源后，用户点击提交到真正锁定之间是否存在竞争？公开页面通常无法回答。

### `confirmation gap`

填写表单 ≠ 收到确认短信/电话 ≠ 预约成立。

### `cancellation/no-show gap`

患者取消、未到、超时，号源可能重新释放，也可能作废。archive 通常看不到。

### `doctor-schedule gap`

医生停诊、替诊、临时排班变化可能改变最终结果。

### `check-in gap`

预约身份与就诊卡/身份证不一致，可能无法取号。

### `visit-outcome gap`

即使取到号，也不能从预约系统推断诊疗、检查、处方或后续结果。

## 10. 规则本身也是动态 backend state

2011 平台有预约次数上限、取消规则和爽约管理。同一患者在同日、同医院、同科室的预约次数受限；多次爽约可能影响后续预约。[11]

这意味着用户可执行性还依赖：

- 历史预约次数；
- 取消时间；
- 爽约记录；
- 欠费/信用状态（部分制度阶段）；
- 是否已存在冲突预约。

这些状态几乎不会进入公开 Web capture。

新增：

### `account-history state gap`

两个用户看到相同网页，后台资格可能完全不同。

因此不要用一张公开帮助页模拟“任意普通用户都能完成”的历史交易。

## 11. 统一平台降低 URL/电话碎片化，也制造新的“中心平台幸存偏差”

2011 统一平台建立前，各医院有自己的电话、预约卡和网站；统一平台之后，公众更容易记一个 `114 + www.bjguahao.gov.cn`。[6]

对旧网研究，这有两个相反效果：

1. **历史用户层**：搜索和记忆成本降低；
2. **历史档案层**：后来研究者更容易找到中央平台相关资料，而忽略此前大量医院自有系统。

这可以叫 **centralization survival bias（中心化幸存偏差）**。

如果只研究后来文献最丰富的统一平台，会错误地把 1999–2010 的多卡、多电话、多站点阶段压扁成一条线。

## 12. 本轮负结果：服务被证明存在，但原始互动页仍未可靠恢复

本轮通过公开 Web 搜索确认了：

- 1999 “北京卫生信息网”预约服务的同期/后续机构性描述；
- 2011 `www.bjguahao.gov.cn` 域名及平台启动日期；
- 2011 注册、短信验证、识别码、取号流程；
- 医院端数据交互和技术容量说明。

但本轮**没有可靠核验**：

- 1999 北京卫生信息网预约页的 A 级历史 capture；
- 2011-07-28 当日 `bjguahao.gov.cn` 首页/注册页/科室选择页的已打开并检查的 WARC/Wayback capture；
- 当时 CSS/JS/charset/browser 依赖；
- 真实 slot API/响应格式；
- 预约锁号、短信网关与医院 HIS 的协议细节。

搜索结果里即使未来出现 Wayback locator，也必须实际打开并检查后才升级为 verified capture。

因此本轮不制作“2011 挂号网站复原截图”。

## 13. 浏览器与客户端环境：目前证据不足，不猜 IE/ActiveX

2000s 中国政务/医疗站点常见 IE、ActiveX、旧编码等环境问题，但**这一事实不能自动套到本案**。

目前没有足够 A 级材料证明 1999/2011 两个预约系统：

- 是否 IE-only；
- 是否使用 ActiveX；
- 是否依赖特定 Java/Flash；
- 是 GB2312/GBK 还是 UTF-8；
- 是否依赖短信插件/安全控件；
- 历史 viewport/DOM 形态。

所以这些必须留在 `unknown`，不能凭时代常识复原。

## 14. 医疗 Web 的隐私 stop condition 比普通论坛更严格

挂号系统可能涉及：

- 姓名；
- 身份证号；
- 手机号；
- 就诊卡/医保身份；
- 医院与科室；
- 就诊日期；
- 医疗记录或检查报告。

这些信息即使曾通过错误配置或历史页面公开，也不应为了“补齐状态机”重新传播。

特别要固定：

> **historical public exposure ≠ present-day ethical republication**。

研究平台结构时优先保存：

- 字段名称；
- 验证规则；
- URL pattern；
- 帮助文档；
- 空白表单；
- 匿名化流程；

而不是患者真实身份或医疗记录。

## 15. 1999–2011 医院预约 Web 的主要 archive gaps

### 15.1 `service-exists / original-artifact gap`

后来档案回顾证明服务存在，不等于原页面已恢复。

### 15.2 `form-shell gap`

空白预约表能证明字段，不能证明提交端点或后台仍存在。

### 15.3 `inventory-partition gap`

某医生总号源如何分给窗口、自有系统、统一平台、复诊和转诊，通常看不到。

### 15.4 `slot-snapshot gap`

号源随分钟变化；单 capture 很容易误导。

### 15.5 `release-time queue gap`

“队列”可能在电话、刷新、放号时刻和提交竞争中，而不是页面上。

### 15.6 `contactability gap`

电话号码被公布，不证明忙线时可接通。

### 15.7 `prerequisite-card gap`

远程入口可能仍要求先线下建卡。

### 15.8 `identity-binding gap`

平台实名、身份证、手机号、就诊卡、医保身份的映射难从公共页面恢复。

### 15.9 `appointment-lock gap`

看到 slot 到真正锁号之间的 race 通常不可见。

### 15.10 `confirmation gap`

提交 ≠ 短信/电话确认 ≠ 预约成立。

### 15.11 `platform-HIS synchronization gap`

统一平台和医院内部系统之间是否及时一致，需要后台证据。

### 15.12 `cancellation/no-show gap`

取消、爽约、释放号源和信用状态往往在后台。

### 15.13 `doctor-schedule gap`

医生临时停诊/替诊不一定被 archive 保存。

### 15.14 `check-in gap`

现场身份核验/取号是否成功，公共 Web 不知道。

### 15.15 `visit-outcome gap`

预约系统不能证明患者最终见到医生，更不能证明诊疗结果。

### 15.16 `proxy-operator gap`

实际点击/打电话的人可能是子女、配偶、单位人员，不是患者本人。

### 15.17 `centralization survival bias`

2011 后统一平台资料较丰富，容易遮蔽此前医院自有预约生态。

### 15.18 `medical-privacy gap`

某些最关键的现实执行记录本来就不应该进入公开 archive。

## 17. 反例与后见之明风险

### 不要写：`1999 年中国人开始网上挂号`

应写：北京已出现早期公众 Web/电话预约服务；同时全国 Internet 用户仍是少数，现场、电话、医院自有系统长期并存。

### 不要写：`网上预约消灭了排队`

队列会迁移到放号时刻、电话忙线、网页刷新和热门号竞争。

### 不要写：`预约成功 = 看上病`

现场身份、到达、医生出诊、取号和候诊仍是独立状态。

### 不要写：`统一平台 = 所有号源`
