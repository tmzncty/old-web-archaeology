# 1999–2006：网上同学录、可变资料与“联系连续性”缺口

> Scope：本文件只处理约 1999–2006 中文旧网中“网上同学录 / 校友录 / 班级空间”作为 Web artifact 时的证据合同。
>
> 更长的普通生活史、1963 纸质通讯录前史、海外 Email/Internet 对照和 2018 以后平台记忆问题，写在：
> <https://github.com/tmzncty/how-people-lived/blob/main/topics/contact-continuity-cohort-addressability-and-portable-social-ties-china-1963-2024.zh-CN.md>
>
> 本文件不把同学录写成“中国 SNS 起源神话”，也不以今天仍存活的门户转载页冒充原始班级页面。目标是回答：**当一个旧班级被做成可搜索的 Web namespace 时，档案今天究竟能证明什么，又系统性看不见什么？**

---

## 1. 为什么这不是另一个“婚恋 profile / job board”案例

仓库已经分别处理：

- 招聘网站中的职位、简历、投递与后台筛选；
- 婚恋平台中的 profile、双向选择、站外联系与关系结果；
- 育儿社区中的年龄分组、潜水者与平台整理；
- 论坛短工、住房 classifieds 等从 Web 进入现实执行的链条。

网上同学录的逻辑不同。

它通常不是先发现陌生人，而是：

> **把一段已经存在的共同过去，转译成一个可搜索、可加入、可更新的在线 namespace。**

因此关键 unit 不是 `candidate profile`，而是：

```text
school
→ cohort / grade
→ class namespace
→ membership claim
→ member profile
→ contact fields
→ posts / messages / photos
→ off-platform endpoint
```

这是一种 **re-addressability infrastructure（重新可寻址基础设施）**。

# 3. 研究单位必须拆开

对一个“网上同学录”案例，至少区分以下对象。

## 3.1 platform

例如 ChinaRen 校友录、5460 等品牌/服务。

平台名称延续不等于技术栈、URL、权限和数据库结构从未变化。

## 3.2 school namespace

某学校在平台里的索引入口。

学校名相同也可能存在：

- 同名学校；
- 校名变更；
- 合并 / 撤销；
- 用户重复创建；
- 错误归类。

因此：

> **school label ≠ verified institution entity**

## 3.3 class namespace

某一级 / 某班 / 某专业的在线空间。

它可能由用户创建，也可能存在重复班级。

所以：

> **class page exists ≠ unique historical class**

## 3.4 account

一个平台账号。

账号本身可能：

- 长期不登录；
- 被盗；
- 忘记密码；
- 更换绑定邮箱 / 手机；
- 由同一人持有多个；
- 无法可靠映射到线下自然人。

## 3.5 membership claim

“这个账号属于某班某人”的声明。

这是独立于 account 的 claim。

2004 年诈骗个案直接说明：

> **membership accepted ≠ offline identity verified**

## 3.6 member profile

个人资料页上的：

- 姓名 / 昵称；
- 性别；
- 城市；
- 工作单位；
- Email；
- QQ / OICQ；
- 电话；
- 地址；
- 自我介绍。

这些字段可能在不同时点被修改。

因此：

> **profile field ≠ timeless fact**

## 3.7 class content

留言、公告、相册、活动、讨论等。

一条班级内容存在，不等于所有成员看见或参与。

## 3.8 off-platform endpoint

Email、QQ、短信、电话、线下见面。

这些通常决定关系是否继续，却往往不在同学录 archive 内。

# 4. 一个更准确的“联系连续性”状态机

不要把 `registered` 写成 `kept in touch`。

建议至少拆成：

```text
class namespace created
→ namespace discoverable
→ former student finds namespace
→ account created / logged in
→ membership requested
→ membership accepted
→ profile/contact state visible
→ class content read
→ message/reply interaction
→ off-platform contact exchanged
→ phone / QQ / Email / meeting occurs
→ relationship remains reachable
→ contact state changes
→ profile updated or becomes stale
→ platform/activity declines
→ tie migrates elsewhere or disappears
```

任何一层都可能停止。

因此硬规则：

> **class exists ≠ class active**

> **member listed ≠ member active**

> **member listed ≠ identity verified**

> **profile visible ≠ profile current**

> **message posted ≠ message read**

> **reply ≠ long-term contact**

> **contact field visible ≠ contact endpoint still valid**

> **platform abandoned ≠ relationship ended**

> **platform retained ≠ relationship alive**

# 5. cohort addressability：班级 namespace 是一种不同于个人搜索的路由机制

网上同学录的重要 artifact 不是单一 profile，而是“共同过去”被结构化。

用户可以先知道：

```text
学校 + 入学/毕业年份 + 班级
```

而不知道：

```text
此人当前住址 / 单位 / 电话 / Email
```

仍可能先进入共同班级，再寻找人。

这意味着：

> **shared historical affiliation becomes a routing key**

对旧网考古来说，研究班级 namespace 时应尽量记录：

- URL pattern；
- school / class identifier；
- class title；
- create date（若平台可靠提供）；
- member count（只作为当时页面显示值）；
- join / approval mechanism；
- visible contact fields；
- public vs login-gated；
- message / album / announcement endpoints；
- search discoverability。

绝不能把页面显示的 `member_count` 直接写成现实同学人数或活跃人数。

# 6. mutable-profile time collapse：可变资料会把生命历程压扁成“最后状态”

这是本轮最重要的新 archive problem。

假设一个普通用户：

```text
2001  北京上学，宿舍电话 A
2003  上海工作，手机 B
2005  广州工作，QQ C
2007  换工作，Email D
```

如果平台只有一页可编辑 profile，那么服务器当前状态很可能只保存最后一次值。

今天即使 archive 到 2005 页面，也不能在没有 capture datetime 的情况下自动知道：

- 这项资料什么时候填写；
- 是否已经过期；
- 以前是什么；
- 哪一次迁移导致修改。

因此新增：**mutable-profile time collapse（可变资料的时间塌缩）**。

### 最低要求

研究 contact-state mutation 时，至少应尝试获得：

1. 同一 profile / class 的 ≥2 个历史 capture；
2. 每个 capture 的明确 Memento-Datetime；
3. 原始 URL 与 archive URL 分离；
4. 字段变化表；
5. 页面模板变化与真实 profile 变化分离。

### 禁止

> current value → 反推整段历史

例如今天看到“城市：上海”，不能写“该用户毕业后一直在上海”。

# 7. roster-state overwrite：成员名单也可能只有当前态

班级 roster 不是静态史料。

可能发生：

- 新成员加入；
- 账号被删除；
- 平台清理；
- 昵称修改；
- 成员退出；
- 误加入被管理员删除；
- 同一线下个人重新注册。

如果只保存了一个时点：

> **current roster ≠ historical membership sequence**

因此一个 2005 年 capture 上“20 人”不能证明：

- 2002 年也是 20 人；
- 曾经从未有过第 21 人；
- 20 个账号对应 20 个不同自然人；
- 20 人都看过某条公告。

---

# 8. contact-graph survival gap：最重要的“谁还能找到谁”往往最难存档

公开首页可能被 Wayback 保存，但真正决定关系连续性的部分经常是：

- 登录后成员表；
- 站内消息；
- 私有联系方式；
- 好友 / 同学关系图；
- 搜索结果；
- 加入审批；
- 群发通知；
- Email / QQ / 手机 handoff。

因此新增 **contact-graph survival gap**：

> 公开 Web 能保存“这个班级/平台存在”，却未必能保存“谁在什么时点实际还能联系到谁”。

这类 gap 不能用现代爬虫“补齐”。

如果历史数据本来需要登录或包含普通人联系方式，应优先记录结构与缺失，不重新公开个人敏感字段。

---

# 9. query-state survival gap：搜索框能留下，某次搜索的结果可能完全消失

同学录常见流程：

```text
输入学校 / 姓名 / 年级
→ 动态请求
→ 数据库搜索
→ 返回班级 / 人员结果
```

Archive 可能保存：

- 搜索表单 HTML；
- JS；
- 一些静态 school list。

却未必保存：

- 当时数据库状态；
- POST 请求；
- 登录 session；
- 某个用户在某天看到的具体结果。

所以：

> **search interface survived ≠ historical search result reproduced**

如果现代回放中搜索按钮失效，只能写“dynamic search execution not preserved”，不能用今天的平台数据库替代历史数据库后称为原始复原。

---

# 10. identity-verification gap：共同记忆既是路由键，也是攻击面

2004 年诈骗个案说明：

```text
知道学校信息
+ 能进入/观察同学录
→ 更容易构造“我是旧校友”的可信叙事
```

因此研究网上同学录时应额外记录：

- 是否实名；
- 是否需要邀请码；
- 谁批准加入；
- 是否展示管理员；
- 是否有身份验证提示；
- 是否允许普通成员查看详细联系方式。

但必须避免后见之明：

> 缺少现代 KYC ≠ 当时平台“没有安全设计”。

要具体写它当时提供了什么验证机制，以及机制在哪里失败。

---

# 11. audience-boundary collapse：半私密通讯录的实际受众可能扩大

2005 年隐私争议材料提示：

```text
user enters contact data
→ intended visibility: classmates
→ platform search / scrape / third-party aggregation
→ wider audience
```

这需要把两个对象分开：

- `intended_audience`
- `observed_or_claimed_audience`

因此：

> **privacy setting ≠ guaranteed audience boundary**

同时也不能从一次媒体报道反推平台所有用户数据都遭遇同样处理。

### 隐私纪律

本仓研究这类历史页面时：

- 不批量重列普通人的姓名、住址、电话、Email、QQ；
- 若来源新闻必须引用个案，只保留支持 claim 的最少角色信息；
- 不因为数据今天仍可搜索，就重新构造大规模历史联系人数据库。

---

# 12. off-platform handoff gap：同学录越成功，后续关系越可能离开它

一个人从同学录找到旧同学以后，常见下一步可能是：

```text
站内留言
→ Email
→ OICQ / QQ
→ SMS / phone
→ meeting
```

2001 年移动 OICQ 还说明 QQ/OICQ 自身已经可以跨 Internet 与短信网络。

于是：

> **online class is often a discovery / routing layer, not the whole relationship system**

对 archive 来说，这形成悖论：

- 平台页面保存了“重新找到”的入口；
- 真正之后十年的联系可能全部发生在不可公开归档的系统里。

因此：

> **successful re-contact can reduce the amount of later evidence on the original website**

---

# 13. activity ≠ intimacy：页面活跃度不能替代关系强度

2005 年《解放日报》同一篇报道提供一个重要反例：

- 远距离毕业生可以靠网上班级继续联系；
- 同时，在同一校园里的学生如果过度依赖网上交流，也可能减少现实串门和集体活动。

所以 old-web artifact 只能直接证明：

- posts existed；
- replies existed；
- class page had activity；
- users said it helped maintain contact。

不能仅凭：

- 发帖多；
- member count 高；
- 留言频繁；

推出：

> 关系更亲密 / 班级凝聚力更高。

必须坚持：

> **activity ≠ intimacy**

# 14. 平台生命周期以后：关系执行与记忆保管会分离

本仓主 scope 到约 2015，本节只作为旧网 artifact 的 afterlife 边界，不扩展成 2018 平台史。

2018 年人人网社交业务出售时，媒体采访到早期用户：

- 有人多年不再使用平台，日常社交已经迁往其他工具；
- 有人忘记账号或密码；
- 有人重新登录只为了查看旧照片 / 日志；
- 有人担心平台关闭或转型而导出数据；
- 也有人因为不确定数据所有权而主动删除。

来源：
<https://finance.sina.com.cn/chanjing/gsnews/2018-11-19/doc-ihmutuec1446027.shtml>

### evidence

- 2018 的导出 / 删除 / 回访行为：**B，同期采访**；
- 对 2006 左右使用方式的叙述：**C，回顾性。**

### 对旧网考古的意义

新增 **memory-custody divergence**：

```text
active relationship graph migrates away
while
old platform retains historical photos / logs / traces
```

因此：

> **data retained ≠ relationship active**

> **data deleted ≠ historical relationship never existed**

平台关闭风险还会反过来促使用户改变 artifact 本身：导出、删除、清空、忘密、弃号。

# 16. 关键边界表

| 可观察 artifact | 可以证明 | 不能直接证明 |
|---|---|---|
| 班级页面存在 | 某时点有该 namespace artifact | 班级长期活跃 |
| member count | 页面当时显示该数值 | 独立真人数 / 活跃人数 |
| 成员 profile | 该 capture 中显示这些字段 | 字段永远真实 / 当前仍有效 |
| QQ / Email / 电话字段 | 某时点页面暴露/记录该 endpoint | 对方实际使用 / 仍有效 |
| 加入班级 | 账号通过当时加入流程 | 线下身份已验证 |
| 一条留言 | 有内容被提交并呈现 | 全班看过 |
| 回复 | 至少发生一次页面交互 | 长期友情保持 |
| 搜索框 | 界面支持某类搜索入口 | 历史数据库结果可复现 |
| 记者写“有数千班级” | 媒体在当时观察/转述该显示值 | 数千活跃真实班级 |
| 隐私设置 | 平台提供或声称有 audience control | 第三方绝不能抓取 |
| 平台后来沉寂 | 该平台关系执行减少 | 原关系已经断裂 |
| 旧照片/日志仍在 | artifact/data retained | 关系仍活跃 |

# 17. 浏览器 / 编码 / 回放条件

本轮来源主要是 contemporaneous secondary evidence，还没有拿到一组可完整验证的原始同学录 capture。

未来若进入 archive 实证，应特别检查：

- GB2312 / GBK；
- table / frameset 布局；
- 登录 cookie；
- 动态查询参数；
- POST；
- JS form submission；
- 头像 / 相册子资源；
- URL rewrite；
- archived search results 是否只是 replay shell；
- 登录页是否覆盖了原班级页面；
- 旧域名是否已复用。

现代 Chromium 打开一个班级 URL，不能证明 2003 年 IE 用户看到相同页面或功能。

# 18. 已证实 / 高概率 / 不知道

## 已证实

- 2004 的公开用户教程记录了 ChinaRen 校友录的班级搜索/创建操作；
- 2005 同期报道记录了异地实习、毕业迁移后使用网上班级继续联系的具体用户；
- 2004 已有冒充同学身份进入班级并利用信任的同期个案；
- 2005 已有“原本只给同学看的联系方式被第三方展示”的同期隐私争议；
- 2001 已有 OICQ 与手机短信的跨网通信服务，说明 off-platform contact 本身也可能跨终端。

## 高概率但当前不能写死

- 网上同学录降低了不知道旧同学当前地址时的 re-contact cost；
- 可变 profile 相比纸质通讯录更适合维护迁移后的联系状态；
- 许多关系找到对方后会转到 QQ / Email / 电话继续，因此原平台低估后续关系持续时间；
- 同一个 profile 的历史状态很可能因编辑覆盖而系统性丢失。

## 目前不知道

- 典型班级的真实活跃寿命；
- 多久登录一次才算“保持联系”；
- 多少账号是重复、弃用或误认；
- 一个 profile 每次搬家/换号是否及时更新；
- 某个班级最后迁往了哪个平台；
- 原始站内私信 / 加入审批 / 联系图谱能否在合法隐私边界内找到历史证据；
- 5460 / ChinaRen 等具体平台在不同年份的搜索与隐私默认值是否发生过版本变化。

# 19. 下一步高价值对象

不要继续收集“平台有多少注册用户”的宣传数字。

优先级更高的是：

1. 找一个 1999–2006 中文网上班级的 **两个以上 verified archive captures**；
2. 比较同一班级 roster 在不同日期的成员变化；
3. 找同一普通 profile 的城市 / 单位 / 联系方式字段怎样更新，但只做隐私最小化记录；
4. 找班级从 `active → graduation → long-distance use → migration to QQ/SNS` 的 contemporaneous chain；
5. 找平台当时关于加入审批、隐私范围、联系方式显示、删除账号的官方帮助页；
6. 找一次真实 `同学录发现 → QQ/电话 handoff → 线下重聚` 的同期第一人称序列；
7. 若只有普通人的已删除敏感页面，不继续扩张，记录 privacy stop condition。

真正值得恢复的，不是一个已经空掉的“同学录首页”，而是一个更困难的问题：

> **这个页面在某个普通人毕业、搬家、换工作以后，究竟有没有成功替他把旧关系继续路由到下一段生活。**
